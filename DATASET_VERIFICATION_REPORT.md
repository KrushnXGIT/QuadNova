# Dataset Verification Report — Phase 1

**Project:** Smartphone-Based Non-Invasive Anaemia Screening
**Phase:** 1 — Dataset Verification
**Scope of this report:** A 6-file **sample** dataset provided directly by the user
(`QuadNova__datazip.zip`), analyzed with `src/data_analysis.py`.

> **Important scope note:** I did not have network access to
> `github.com/KrushnXGIT/QuadNova`, IEEE DataPort, Kaggle, or data.gov.in in this
> session, so `PROJECT_MASTER.md`, `HANDOFF.md`, and `README.md` from the actual repo
> were **not** read, and the full Eyes-Defy-Anemia dataset and NFHS-5 dataset were
> **not** inspected. Everything below is derived only from the 6 sample files supplied.
> Treat this as a **pilot verification on a tiny sample**, not a full-dataset audit.

---

## 1. What Was Actually Provided

6 files, 2 subjects (identified by an 8-digit-date + 6-digit-time filename prefix,
matching the Eyes-Defy-Anemia naming convention):

| Subject ID | Raw photo (.jpg) | `_forniceal` mask | `_palpebral` mask | `_forniceal_palpebral` mask |
|---|---|---|---|---|
| `20200118_164733` | ✅ | ✅ | ✅ | ✅ |
| `20200203_091841` | ❌ **missing** | ❌ **missing** | ✅ | ✅ |

No CSV, JSON, XLSX, or any metadata/label file was present in the archive — **no
Hb values, age, sex, or explicit subject-ID table exist in this sample.**

## 2. Image Format & Dimensions (verified)

- Raw photo: JPEG, **3984×2988**, 3-channel RGB, ~2.45 MB.
- All 4 masks: PNG, **800×1067**, 4-channel RGBA, non-interlaced.
- Filename convention confirms `IMAGE → SUBJECT`: the subject ID is the
  `YYYYMMDD_HHMMSS` capture timestamp prefix shared across a raw photo and its masks.
  There is **no separate patient/subject ID field** — the timestamp *is* the subject key.
- **No Hb value appears anywhere in filenames, EXIF, or PNG metadata.** Hb linkage
  must come from an external metadata table that was not included in this sample.

## 3. EXIF / Capture Metadata (verified, from `20200118_164733.jpg`)

- Device: Samsung SM-G920I (Galaxy S6), captured 2020-01-18 16:47:33.
- `Orientation = 6` (needs 90° CW rotation to display upright) — this is confirmed
  to matter (see §5).
- PNG masks carry a re-embedded `Raw profile type exif` chunk and an Adobe XMP
  packet, consistent with the masks having been generated by an ImageMagick-based
  crop/rotate/resize pipeline from the original JPEG, not hand-drawn independently.

## 4. Data Integrity Finding (confirmed defect)

**All 4 PNG mask files in this sample have a corrupted `iCCP` chunk (bad CRC).**
Verified independently two ways:
- Manual PNG chunk CRC walk (`check_png_crc_integrity` in the script) — all 4 masks fail.
- `libpng`/OpenCV load the files but emit `iCCP: CRC error` warnings for all 4.
- **Plain `PIL.Image.open()` cannot open any of the 4 mask files at all** — it raises
  `UnidentifiedImageError` (wrapping a `SyntaxError: broken PNG file (bad header
  checksum in b'iCCP')`). `cv2.imread(..., cv2.IMREAD_UNCHANGED)` loads them successfully
  and was used for all subsequent analysis.

**Implication for later phases:** if this defect is present dataset-wide (not just
in this sample), any PIL-based data loader (`torchvision.datasets.ImageFolder`,
plain `PIL.Image.open`, etc.) will crash on every mask file unless it either
(a) strips/ignores the bad `iCCP` chunk first, or (b) uses OpenCV/`imageio` instead.
This must be verified against the full dataset before Phase 2 (Data Preparation)
picks a loading library.

## 5. Raw Photo ↔ Mask Geometric Relationship (verified)

For the one subject with both a raw photo and masks:

- Raw: 3984×2988 (landscape, 4:3). Mask: 800×1067 (portrait, ~3:4).
- These are consistent with: **rotate raw photo 90° per its EXIF `Orientation=6` tag,
  then downscale by ~3.735×** (2988/800 = 3.735, 3984/1067 = 3.735 — matches to 3 decimals).
- **Consequence:** masks are *not* pixel-aligned to the raw JPEG as-is. Any pipeline
  that maps mask pixels back onto the raw photo (e.g., to crop full-resolution ROI)
  must replicate this same EXIF-rotate + ~3.735× scale transform, not assume identity
  alignment.

## 6. Mask Semantics (verified)

- Masks are **RGBA cutouts**, not flat-color overlays: pixel color inside the masked
  region is the actual conjunctiva tissue color (mean BGR ≈ [143, 101, 168] for the
  forniceal mask — high red channel, consistent with conjunctival tissue), not a
  synthetic highlight color. This means masks are directly usable as an ROI crop
  (`pixel = raw_pixel where alpha>0, else transparent`), not just a boundary outline.
- For subject `20200118_164733`: `forniceal_palpebral` mask coverage (13.75% of
  frame) equals `forniceal` (5.07%) + `palpebral` (8.68%) to within rounding —
  **confirms `forniceal_palpebral` is the pixel-wise union of the two individual
  masks**, not an independently-drawn region.
- **Mask style is inconsistent across the 2 subjects in this tiny sample**:
  - `20200118_164733` masks are near-binary (2–3 distinct alpha levels — hard edges
    with light anti-aliasing).
  - `20200203_091841` masks have **256 / 254 distinct alpha levels** — soft,
    heavily anti-aliased or gradient-edged masks, a visibly different generation
    method or export setting.
  - This is only n=2, but it's a real, measured difference and should be checked
    across a larger sample before assuming a single uniform mask format
    dataset-wide.

## 7. Subject / Image Completeness (verified, n=2)

- 2 unique subjects. 1 of 2 subjects has **no raw photo at all** in this sample —
  only its 2 masks were included. This could mean the sample archive is simply
  incomplete (likely, given it's explicitly a "sample"), or it could reflect a real
  gap pattern in the full dataset. **Cannot be determined from n=2** — flag for
  Account 2 to check against the full dataset for how common missing-raw-photo
  subjects are.
- With only 2 subjects and no metadata file, **no meaningful data-leakage / images-
  per-subject / train-test-split analysis is possible** from this sample. That
  requires the full dataset and its metadata table.

## 8. Hb Label Statistics

**Not computable.** No Hb values exist anywhere in this sample (no metadata file
was provided). Per instructions, no values are invented.

## 9. NFHS-5

**Not inspected** — not included in this sample, and data.gov.in was not
reachable from this session. Per the source instructions, NFHS-5 is population-level
prevalence data and must **never** be converted into image-level Hb labels regardless
of what the full inspection shows later.

## 10. Feasibility Determination

**C — Neither Hb regression nor Hb classification feasibility can be determined
yet**, strictly because the metadata/label file (the actual Hb-value table) was not
part of what was provided or reachable in this session. This is a **data-availability
blocker**, not a negative finding about the dataset itself — the image/mask side of
the pipeline (§2–§6) looks structurally sound and directly usable for ROI extraction
once the geometry/rotation handling in §5 is implemented and the `iCCP` CRC issue in
§4 is worked around.

## 11. Blockers for Next Steps

1. **No access to the actual GitHub repo, IEEE DataPort, Kaggle, or data.gov.in
   from this environment** — `PROJECT_MASTER.md`, `HANDOFF.md`, `README.md`, and the
   real dataset scale were never read. This report is based solely on the 6-file
   sample the user uploaded directly.
2. **No Hb metadata table available** — the single largest blocker to any
   feasibility decision. Needed before Phase 2 can start in earnest.
3. **`iCCP` CRC corruption** confirmed in all 4 sample masks — needs checking at
   full-dataset scale, and a loader decision (OpenCV/imageio vs. sanitizing the PNGs).
4. Mask anti-aliasing style differs between the 2 sampled subjects — needs
   checking at scale to see if this is a dataset-wide inconsistency.
